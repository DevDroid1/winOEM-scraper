PLAN: next two features (not built yet)
======================================

A. Baseline verification ("is this file really part of stock Windows?")
-----------------------------------------------------------------------
Goal: replace the current heuristics (owner / WinSxS hard link / layout.inf) with a real comparison.
Sources, tried in this order (all optional, the script reports which one it used):
  1. Windows install media or ISO the user points at (like Setup / repair):
       - NT6+ : sources\install.wim (or .esd) - listed with `dism /Get-WimInfo`, files read with
                `dism /Mount-Wim` (read-only) or `/Get-WimInfo` + `wimlib`-free `dism /Export`-less compare,
                matching the installed edition/build index. Drivers: the inbox driver list from the WIM's
                Windows\INF\*.inf (every non-oemNN.inf there is "inbox").
       - NT5  : i386\layout.inf + i386\*.cab / dosnet.inf on the XP/2000 CD (and the I386 folder some
                OEMs leave on C:).
       - 9x   : WIN9x\*.cab + precopy*.cab file lists (`extract /D`).
  2. Local component store as the live reference (NT6, no media needed): WinSxS manifests + the
     servicing catalogs (CBS) say which files belong to Microsoft packages. `sfc /verifyonly` and
     `dism /Online /Cleanup-Image /CheckHealth` use the same data.
  3. Optional shipped baseline: a compact hash list (path, size, SHA-256) per Windows build, kept in
     baselines\<build>.txt. Small for the OS tree (~ tens of MB per build compressed), so only the builds
     the user cares about would be bundled. NOT bundled for every Windows version.
Decision rule per file/driver: Microsoft-signed catalog member (WinVerifyTrust via certutil/`sigcheck`-style
check on Vista+) AND present in the baseline = STOCK (excluded). Hash differs = "stock file replaced by OEM".
Not in baseline = OEM/other. A driver "by HP that is also in a default Windows install" is then reported as
STOCK (inbox) instead of OEM; a driver added by a peripheral is separated using install time vs OOBE end
and the device it binds to (DriverStore + PnP device class), tagged "peripheral / user-added".
IMPORTANT: the media MUST be the same Windows edition AND build as the installed system; the disc that came
with the PC is the best source. No hashes are used: comparison is by path, size and catalog signature.
Risks to state: install media must match edition and build (feature updates change files); media is
large and slow; baseline hashes must come from genuine media; NT5/9x only get name+size comparison.

B. Menu-based TUI
-----------------
JScript/WSH has no raw keyboard input, so a full-screen TUI would need helper tools. Proposed layers:
  - Screen layer in common.js: cls + fixed header + a live "current choices" panel + one menu per screen,
    drawn in plain ASCII (works on every console, including Win9x).
  - Single-key input: `choice` (Win9x, Vista+) so no Enter is needed; Enter-based numbers on XP.
  - Optional arrow-key navigation on Win7+ through a tiny PowerShell helper (ReadKey), auto-skipped when
    PowerShell is absent; the numbered menus remain the fallback.
  - Screens: Home (Name / Location / Preset / Adjust / Baseline / Start) -> each opens its page, returns
    to Home with the summary panel updated. Same screens in the 9x batch where `choice` allows.
